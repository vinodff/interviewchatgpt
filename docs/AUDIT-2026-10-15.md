# Live interview audit — October 15, 2026

The existing application contained two overlapping execution paths: a FastAPI/WebSocket service and a standalone browser workspace on Vercel. Several UI handlers mixed the two, and server fallback routes returned fabricated successful records. This audit makes the choice explicit and repairs the conversation pipeline.

## Confirmed defects corrected

| Area | Failure | Correction |
| --- | --- | --- |
| Continuous speech | Every event replayed previously finalized speech into the next question. | Track consumed recognition results; replace interim hypotheses and give each utterance its own identity. |
| Recognition corrections | A provisional phrase such as “dad structure” could generate an answer before recognition corrected it. | Hold incomplete prefixes, but submit stable complete request cues after 600 ms even when the engine keeps the surrounding speech interim. Match the last request cue, avoid resubmitting the same question as its answer is appended, and deduplicate the eventual final transcript. |
| Speaker estimates | First-person keywords and vocabulary overlap could prevent a real embedded question from being answered. | Send substantive speech to a contextual model decision; speaker attribution and whether to answer are separate outputs. |
| Context | Browser answers lacked prior questions, generated code and candidate speech. | Include bounded recent spoken turns, previous questions/answers/code, job context and relevant source excerpts. |
| Concurrent speech | Candidate narration could abort an unanswered interviewer question. | Bound concurrent requests and queue speech; only a confirmed newer question supersedes older generation. |
| Stale answers | Late responses could affect a newer answer and local speech state. | Check request ownership and generation order before emitting previews or final answers. |
| Answer hold | Browser answers bypassed the display hold used for WebSocket answers. | Route both modes through the same generation-aware delivery/hold mechanism. |
| Transcript identity | Cross-pause corrections reused the ID of a following utterance. | Advance identity after each dispatch, including corrected continuations; finalize filler previews. |
| Capture lifecycle | Unsupported recognition and permission failure could leave a misleading listening state. | Show a terminal error, stop the session, dispose pending work, and bound restarts. Backgrounding stops browser capture explicitly. |
| Answer latency | Browser generation waited for the full answer and duplicated large instructions. | Stream provider SSE into same-origin NDJSON previews; display actual answer text while generation continues. Use a 600 ms pause for complete phrases and a longer hold for incomplete prefixes. |
| Gemini availability | Unavailable models and unsupported thinking settings prevented fallback. | Default general requests to Gemini 3.6 Flash with `minimal`; use `low` for Gemini 3.8 Flash, including code requests. Keep credentials server-only and try at most two distinct models. |
| Partial streams | Invalid provider data could leave its body active or start a second model after text had already appeared. | Cancel readers on errors; prohibit model switching once a preview has been emitted; reject truncated final responses. |
| API proxy | Backend errors silently became fake successes, loopback URLs were ignored, and response cookies were lost. | Preserve backend status, body, cookies and authentication; never fall back to a fabricated workspace. |
| Origin checks | Next's internal hostname could differ from the actual browser host and reject valid requests. | Validate the browser origin against the forwarded/request host and reject cross-site calls. |
| Persistence | Project, upload and profile actions could report success without surviving reload. | Use explicit browser storage for standalone mode and authenticated API storage for backend mode. |
| Evidence | Unreadable files, repository URLs and empty profiles generated invented, “verified” experience. | Only retrieve extracted, relevant text; uploaded claims remain unverified. Unsupported browser formats/imports fail explicitly. |
| Storage quota | A multi-key upload could leave a “ready” orphan when content storage failed. | Roll back the document save and report the quota/storage error. |
| Retention | Disabled transcript retention was ignored; updated answers could duplicate history turns. | Honor retention and replace existing turn IDs without double-counting questions. |
| Deletion | Deleting a source or project left its full text stored separately. | Remove associated source content and search chunks. |
| Profile | Duplicate role/company fields caused one set of edits to be silently ignored. | Render a single profile context field set. |
| Authentication/errors | Failed logout and failed provider checks appeared successful. | Preserve the authenticated UI on failed logout and show real provider/save errors. |
| Backend speakers | Multipart interviewer questions and constraints were split into fabricated candidate turns. | Preserve authoritative audio-channel roles; split mixed audio only when complete, disjoint model spans occur in the transcript. |
| Reconnect order | Equal database timestamps could reverse conversational turns. | Serialize retained writes and allocate strictly increasing timestamps per session. |
| Retrieval | Query embedding timeout exceeded the live answer budget, preventing lexical fallback. | Bound query embedding to five seconds and fall back to tenant-scoped lexical retrieval. |

## Verification

- Frontend: **163 tests passed**; ESLint, TypeScript and `next build` passed.
- Backend: **172 tests passed** using an isolated SQLite test database, memory coordination and no provider credentials. Ruff passed. One dependency deprecation warning remains.
- Browser: **2 Playwright journeys passed** against a production build. Projects, profile, text upload, evidence search, reload persistence, deletion and mobile width were exercised. The live journey replaced speech hardware only; app storage, API requests and Gemini responses were real. It exercised recognition correction, candidate narration, follow-up context, the screenshot sequence with a trailing “what is list” inside an interim candidate explanation, and disabled retention. The earlier journey also passed against the public Vercel site.
- Real provider probes reproduced Gemini 3.5 Flash-Lite HTTP 503 `UNAVAILABLE` and Gemini 3.8 Flash rejection of `MINIMAL`. Gemini 3.8 `LOW` and Gemini 3.6 `MINIMAL` responded successfully.
- Latest local streaming samples showed first answer text at **1.66–2.31 seconds after API submission**, with full replies at **2.11–2.77 seconds**. These are three observations, not a latency guarantee; browser recognition, phrase pauses, network and provider load add variability.
- Public Vercel health and streaming calls returned HTTP 200. A production sample delivered first answer text at 1.45 seconds and completed at 1.96 seconds after submission.
- No Meesho image URL or product ID from the reported console error occurs in the project source. Its origin was not established by the provided console message.

## Deployment and practical boundaries

The Vercel deployment uses `NEXT_PUBLIC_WORKSPACE_MODE=browser` with its existing server Gemini credential. The FastAPI fixes are included in the repository and require deployment of that separate backend to affect a hosted WebSocket installation.

The browser workspace stores data on the current device. It supports readable text PDFs, text/Markdown and source files. OCR, DOCX ingestion, actual GitHub imports/identity verification, billing, cross-device account storage and separate meeting-tab audio require the full backend. Older uploads that were synthesized by previous versions should be removed and re-uploaded from their actual source documents.

Speaker identity cannot be guaranteed from one mixed microphone. For the strongest interview capture, use the full backend with a dedicated permitted interviewer audio track and a separate candidate microphone. On iPhone, browser microphone capture requires the page to remain active and must actually hear the interviewer; this work does not grant access to another app's audio. A physical iPhone microphone/permission test remains outstanding.
