# Faster contextual answers — October 16, 2026

The latency work targets the existing Vercel browser workspace and its optional **Enhanced microphone · quiet voices** capture mode. Standard browser recognition keeps its adaptive early-question detection and streamed text answers. The separate FastAPI/WebSocket service was not changed in this phase.

## Changes

- Reduced the Enhanced segment's silence wait from 1,200 ms to 600 ms and the continuous segment cap from six seconds to four. Pre-roll, overlap assembly and capture-timestamp-based incomplete-question continuation remain enabled.
- When uploaded-source retrieval is unnecessary, a single Gemini call transcribes the clip, recognizes the latest request using session memory, and streams its answer. This removes the previous transcription-then-answer round trip. The combined audio default is `gemini-3.1-flash-lite`, with `gemini-3.6-flash` fallback before any preview is shown. `GEMINI_AUDIO_ANSWER_MODEL` overrides the audio default; `GEMINI_ANSWER_MODEL` overrides all answer models.
- Source-based personalization still transcribes first, retrieves evidence for the actual question, and streams a grounded answer. Technical personalization can use the single-call path even when sources exist. The optimization does not bypass grounding or treat candidate narration as verified experience.
- A prepared answer is reused only for the exact current speech and matching preferences/active task. Expired prefixes, newly available sources and changed context invalidate it. Explicit or contextual requests that the audio model declines still get the text intent check, preventing a missed “Now in JavaScript” follow-up.
- Audio previews reach the existing answer lifecycle immediately. The transcript and decision metadata cannot change midway through a stream. Failure, truncation and Stop cancel an unfinished preview before the session ends. Partial code is never reported as a completed answer. Stop aborts capture and pending requests; late responses cannot revive the session.

The endpoint retains same-origin/header checks, bounded context, strict WAV validation, server-only credentials, per-instance request limits and at most two provider attempts. Four-second client clips fit the unchanged six-second server audio limit; the body limit is now 400,000 bytes to include bounded interview context alongside the WAV.

## Measurements

The same synthetic quiet “What is a Python dictionary?” recording was passed through Chromium's real getUserMedia/AudioWorklet path, normalized WAV processing, the real Gemini provider and answer rendering. The fixture is attenuated by 34 dB, with input RMS around −55 dBFS and startup silence before the question. No capture implementation, application response or provider response was mocked.

Elapsed time is measured to the first visible answer text, relative to an estimated last voiced sample in the fixture. It includes capture buffering and network/provider processing. These are small samples, not a production percentile study or physical Android acoustic measurements.

| Run | Samples after estimated speech end | Median | Requests for that question |
| --- | --- | --- | --- |
| Previous production | 5.773, 5.859, 5.966 s | 5.859 s | Audio transcription + text answer |
| Final local production build | 3.620, 3.625, 4.800 s | 3.625 s | One streamed audio-understanding call |
| Updated production | 3.330, 3.089, 3.549 s | 3.330 s | One streamed audio-understanding call |

The public before/after sample shows a 2.529-second reduction in median first-text delay (about 43%). All three updated production recordings reached a complete answer through the single-call path. This is a six-run before/after comparison with a fixed synthetic question, not evidence that every real interview question will achieve these times.

Later that day, the [short-topic and recent-question release](RECENT-QUESTIONS-2026-10-16.md) added intent and reference-selection changes. Its three production measurements were 5.195, 3.690 and 4.725 seconds (median 4.725 s). The 3.330-second figure above describes the earlier speed-only sample, not a fixed or current guarantee.

Provider load and network conditions still affect individual runs. Source-based requests retain their evidence retrieval path, and complex answers can take longer to finish even when the opening text appears quickly. No fixed latency guarantee is made.

Direct provider probes compared the combined audio models with identical prompts. Five scenarios per model covered embedded questions, first-person code requests, candidate narration, quoted past questions and a contextual language conversion. Both models passed the intent/topic checks. The lighter model returned first text faster in those sampled requesting cases. A stricter code check exposed a missing-code response from the lighter model; the audio instruction was strengthened to require working fenced code for sufficiently specified implementation requests. Two repeats of both code scenarios per model then passed fence, push/pop, language and selected complexity checks. The final stricter benchmark also passed with actual provider model attribution verified, rather than crediting a fallback to the requested model. This checks selected content, not exhaustive algorithm correctness.

## Verification

- Three repeated real-audio latency journeys passed against the final local build. The two standard browser journeys and the quiet/slow audio journey also passed together. The slow fixture contains a 1.8-second pause inside the question; the complete question still reached an answer. Stop released microphone tracks and opted-out retention left session turns empty.

Ignored `data/latency-*-2026-10-16.json` and `data/audio-answer-*-2026-10-16.json` retain local synthetic measurements. No user recordings or provider credentials are included in those reports. Physical Android microphone sensitivity, Bluetooth routing, room noise and simultaneous meeting-app capture remain unverified on actual hardware.

## Repeat the measurements

Start a browser workspace with a configured server Gemini credential, then run:

```powershell
cd frontend
$env:E2E_BROWSER_MODE='1'
$env:E2E_BASE_URL='http://127.0.0.1:3022'
$env:E2E_QUIET_AUDIO_FILE='C:/absolute/path/to/synthetic-quiet-fixture.wav'
# Optional: the fixture's estimated voice-end time, including leading silence.
$env:E2E_VOICE_END_MS='3667'
npx playwright test tests/e2e/enhanced-microphone.spec.ts --repeat-each=3
```

The journey saves `voice-latency.json` in each Playwright test output directory. Copy it before another Playwright run clears that directory. Omit `E2E_VOICE_END_MS` for a different fixture unless its last voiced sample was measured separately.

The direct model comparison is opt-in and uses synthetic audio only:

```powershell
# GEMINI_API_KEY must be configured in this test process; never log it.
$env:AUDIO_BENCHMARK_FILE='C:/absolute/path/to/synthetic-dictionary.wav'
npx vitest run tests/audio-latency-benchmark.test.ts
```

`AUDIO_BENCHMARK_MANIFEST` optionally supplies an array of synthetic fixtures with `id`, `audio_file`, `expected_request`, optional `topic_pattern`, `transcript_pattern`, `required_patterns`, `forbidden_patterns` and a prior `seed` question/answer. `AUDIO_BENCHMARK_REPEATS` accepts 1–10; reports distinguish requested and actual provider models.
